# Development plan

PyrixOS is designed before it is built. Each phase starts only when the one before it is complete, and implementation starts only when its RFC is accepted.

| Phase | Scope | Deliverables | Done when |
| --- | --- | --- | --- |
| 0. Architecture RFC | Agree the design of the language, the build sandbox, the store, the garbage collector, profiles and binary caches | RFC 0001 PyrixOS Architecture, published on the documentation site | The RFC has been reviewed in public, its open questions are resolved or deferred to named follow-up RFCs, and its status is Accepted. |
| 1. PyBonsai evaluator | Interpret a restricted Python syntax tree and produce deterministic derivations | Hermetic evaluator, derivation format, Lattice standard library, `Lattice` library interface with Pydantic data models, `lattice daemon` with JSON-RPC and REST over its Unix socket and TLS, `Client`, evaluator and daemon test suites | Permitted constructs evaluate correctly. Imports, `while`, I/O, mutation, recursion, dunder access and unsupported nodes are rejected. Identical derivations hash identically on different machines. A file evaluates to the same derivations through the library, the daemon and the remote API, and callers without a permitted role or credential are refused. |
| 2. Build sandbox | Run builds in isolated, hardened Linux namespaces with no network access | Namespace backend, seccomp filter and resource limits, fixed build environment, sandbox filesystem, build runner, `lattice sandbox-config`, sandbox test suite | Builds run in user, mount, network, PID, UTS and IPC namespaces with no new privileges. Network access, writes outside `/build` and the build's own outputs, and creating setuid files fail. The build environment is fixed. Missing outputs fail the build and temporary state is removed. |
| 3. Store and garbage collector | Keep build outputs in an immutable store tracked in SQLite | Store publication, dependency database, garbage collector, `lattice build --check`, store test suite | Outputs move atomically into the store and become read-only. Writes to the store fail. Collection keeps everything reachable from a root and removes the rest. Rebuilding a reproducible path with `--check` reports no differences. Users without write access to the store build through the daemon, and only the daemon writes to the store. |
| 4. Profiles and stacks | Select what is active through generations, with one active stack per slot | Profile generations, rollback, stack slots, activation with kernel module checks, activation test suite | Switching and rolling back are atomic. A slot never holds two stacks. Kernel modules change only while their devices are unused, and a stack in use by a running process is never collected. Through the daemon, a user switches only their own profiles. |
| 5. Binary caches | Fetch prebuilt store paths instead of building them | Cache format, signing, SLSA provenance, `lattice push`, HTTP substitution, CernVM-FS full copies and shallow paths, `lattice materialise`, cache test suite | Unsigned or altered paths are rejected. A path fetched from a cache is identical to one built locally. Shallow paths work as slots, kernel modules are always local, and collection removes only the symlink of a shallow path. Every published path has signed provenance, and a machine that requires provenance rejects a path without it. |
| 6. Container and microVM backends | Run builds in an OCI container runtime or a lightweight virtual machine for stronger isolation and less dependence on the host | OCI backend, microVM backend for Firecracker, Cloud Hypervisor and OpenVMM with the guest kernel and init as store paths, backend test suite | The same derivations give identical outputs on every backend. The virtual machine has no network device. An unavailable backend stops the build instead of falling back to a weaker one. |

Every phase delivers its features through three interfaces at once: as methods of the `Lattice` Python class, through `lattice daemon` on its Unix socket, and through the remote API over TLS, in both JSON-RPC and REST style. The `lattice` command only calls those methods. Programs other than the command can therefore use each feature as soon as its phase is complete (RFC 0001 sections 6.1 and 6.2).

Phases 1 to 6 each report timing for their main operation. These are evaluation time per syntax tree node, sandbox setup and teardown time, virtual machine boot time, garbage collector traversal time, substitution time, and time to first open of a file in a shallow path.
